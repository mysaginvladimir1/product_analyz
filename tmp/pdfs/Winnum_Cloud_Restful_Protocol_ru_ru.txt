Введение 
Назначение документа 
Все взаимодействие между устройствами и( -или) изделиями (далее устройствами) и защищенным 
хранилищем больших данных (далее хранилищем)  ведется посредствам внутреннего протокола 
WINNUM Restful, который разработан на базе архитектуры Restful с построением связи на уровне 
протокола HTTP/HTTPS. Структура обмена данными( -пакетами) четко регламентирована. 
Настоящий документ описывает базовые команды и структуру пакетов.  
Регистрация устройств 
Для начала обмена данными с защищенным хранилищем все устройства должны быть 
зарегистрированы. При регистрации каждому устройству присваивается уникальный 
идентификатор, состоящий из 41 знака, например, E028707D-8267-46D5-8045-E833146AB3C4, 
резервируется область памяти и предписывается указание для обработки данных (в случаи их 
получения). После регистрации уникальный идентификатор устройства прописывается в хранилище 
и хранится в нем неограниченный промежуток времени. Допускается одновреме нная регистрация 
одного устройства на нескольких хранилищах.  
Принцип обмена данными 
Весь обмен данными между устройствами и хранилищем выполняется на базе протокола WINNUM 
Restful. Использование RESTful API не предполагает хранении сессий т.е. каждое соединение для 
клиента и для сервера является новым , однако, для целей ускорения процедуры проверки 
валидности данных многие команды возвращают ключ, который можно использовать повторно. 
 
Для сохранения данных, помимо уникального идентификатора устройства, необходимо знать (и 
указывать в пакете) идентификатор сигнала или сигналов (при пакетной отправке данных). 
 
 
 
Идентификаторы устройств, идентификаторы его сигналов, а также типы данных сигналов доступны 
WINNUM Platform или могут быть созданы на базе WINNUM Restful. Допускается указание в пакете 
любого идентификатора сигнала и( -или) типа данных . Идентификаторы сигнала должны 
указываться только в кодировке ASCII. Не допускается указывать не существующий идентификатора 
устройств устройства. В случае указания не существующего идентификатора устройства хранилище 
приостановит обработку.

Типы данных сигналов 
Введение 
При получении данных хранилище выполняет их форматирование согласно указанному типу. Все 
типы данных сигналов можно условно разделены на два типа:  
− регулярные 
− нерегулярные 
Разделение является условным и в первую очередь означает принадлежн ость данных. Под 
регулярными типами понимается классические типы данных (различные числа, символы и строки, 
время и дата). Под нерегулярными типами понимается типы данных для работы с памятью 
контроллеров (биты, байты, машинные слова, числа указанной разме рности и т.д.). При отправке 
данных в хранилище допускается использование любых, как регулярных, так и нерегулярных типов 
данных.

Описание протокола WINNUM Restful 
Общая информация 
Для обмена данными с хранилищем нужно знать следующие параметры: 
i) Адрес хранилища (IPv4/IPv6 адрес, где зарегистрировано устройство) 
ii) HTTP и(-или) HTTPS порт облака 
iii) URL и метод команды (основные URL: rest/auth/* и rest/unauth/*, основные методы: 
PUT, POST и GET1) 
 
Важно: регистр везде имеет значение.  
 
Отличие префиксов auth от unauth заключается в том, что все запросы, поступающие через URL 
auth требуют авторизации (указания имени пользователя и пароля), а поступающие через URL 
unauth НЕ требуют авторизации.  
 
В конфигурационных параметрах WINNUM Cloud (параметр – «Cloud.JAXUnAuthServices.Block» 
файл по умолчанию – «config/cloud/mgmt-application.xml») допускается установка блокировки 
для всех запросов, поступающих через URL unauth. По умолчанию все запросы разрешены. 
 
Передаваемые значения 
Протокол WINNUM Restful поддерживает три типа передаваемых с URL командой: 
1. URLENCODED - данные передаются в составе параметров URL команды. Пример 
передачи значений sn, seca и secl в составе параметров URL:  
 
http://10.1.0.1:81/WinnumCloud/rest/auth/reg/url/{uuid}?sn=foo&seca=foo&secl=f
oo 
 
Пример записи значения 1.2 в сигнал B101: 
http://10.1.0.1:81/WinnumCloud/rest/auth/put/url/0C5D7C28-B17D-4E55-A9AB-
71746E58C1B7?id=B101&type=18&value=1.2 
 
2. JSON – данные передаются в теле запроса в виде JSON объекта или списка JSON объектов. 
Пример передачи объекта типа JSON в теле запроса с использование библиотеки RestSharp 
в Microsoft Visual Studio C#:  
 
using RestSharp; 
 
RestfulRequest cRestfulRequest = new RestRequest( "/rest/unauth/put/{uuid}", 
Method.PUT ); 
cRestfulRequest.AddUrlSegment( "uuid", "указать нужный Product UUID" ); 
 
cRestfulRequest.RequestFormat = DataFormat.Json; 
RestfulRequest.AddJsonBody( cCloudCache ); 
 
RestClient cRestfulClient = new RestClient( "http://10.1.0.1:81/WinnumCloud" ); 
cRestfulClient.Encoding = Encoding.UTF8; 
IRestResponse cRestfulResponse = cRestfulClient.Execute( cRestfulRequest );

GET с передаваемыми значениями типа URLENCODED

В примерах указан некий объект cCloudCache. Объектом cCloudCache может быть любой класс (на

Restful: ID, TYPE, VALUE, EVENT, PID, SEQ. Пример класса: 
 
public class CloudCache { 
 private string signal_id = "", signal_value = "", signal_event = "", signal_pid = ""; 
 private int signal_type = -1; 
 
 public CloudCache(){ }

  get { return signal_id; } set { signal_id = value; } 
 } 
 
 public int TYPE { 
  get { return signal_type; } set { signal_type = value; } 
 } 
 
 public string VALUE { 
  get { return signal_value; } set { signal_value = value; } 
 } 
 
 public string EVENT { 
  get { return signal_event; } set { signal_event = value; } 
 } 
 
 public string PID { 
  get { return signal_pid; } set { signal_pid = value; } 
 }

RestfulRequest cRestfulRequest = new RestReque st( "/rest/unauth/put/array/{uuid}", 
Method.PUT ); 
 
Отправленные в виде списка сигналы будут сохранены для одного указанного устройства.  
 
Возвращаемые значения 
Вне зависимости от URL и метода команды WINNUM Restful всегда возвращает JSON объект, у 
которого всегда есть атрибут " status", который показывает статус операции и атрибут " message", 
который показывает описание статуса. По данной структуре всегда можно понять успешно ли 
выполнилась команда или нет. Структура возвращаемого JSON объекта: 
 
{ "status" : "success|error|warning" , "took":4, "message" : "success|описание 
статуса", … } 
 
Пояснения к передаваемым и возвращаемым данным 
Протокол WINNUM Restful для работы с сигналами использует поля: ID, TYPE, VALUE, EVENT, PID 
и SEQ. Описание полей: 
• ID – уникальный идентификатор сигнала. Передается в виде строки. Пример: A55 
• TYPE – тип данных сигнала (см. таблицу регулярных и нерегулярных типов). Передается в 
виде целого числа. Пример: 18 (double) 
• VALUE – значение сигнала. Передается в виде строки. Пример: FF11 
• EVENT – не обязательное значение даты и времени сигнала. Если значение не указывается, 
то будет установлено текущее время WINNUM Cloud. Передается в виде строки формата 
yyyy-MM-dd HH:mm:ss либо yyyy-MM-dd HH:mm:ss.SSS. Пример: 2017-08-22 14:55:31 
• PID – не обязательное значение серийного номера другого устройства на которое 
необходимо продублировать данные. Передается в виде строки. Пример: 555-333-111

• SEQ - опциональный параметр указывающий на то, что значение сигнала это 
последовательность значений разделенных символом - |, которые нужно записать с 
интервалом в миллисекундах указанный в качестве значения SEQ. Например: если значение 
сигнала VALUE=4.5|4.6|4.7, а SEQ=60, то это значит, что пришло три сигнала со значениями 
VALUE=4.5, VALUE=4.6 и VALUE=4.7, время между каждым сигналом составляет 60 
миллисекунд   
 
 
Для хэш сигналов дополнительно возвращаются следующие поля: 
• HASH_TYPE – тип хэша 
• HASH_SIZE – целевое значение количества сигналов в хэше 
• HASH_COUNT – реальное значение количества сигналов в хэше 
• HASH_SCALE – дискретность хэша, например: 0.001 – 1 миллисекунда, 1.0 – 1 секунда. 
 
Пояснения при получении данных через команды unauth/GET и auth/GET 
Если не указан параметр from, то параметр scale не учитывается и по умолчанию сортировка 
результатов выполняется от нового к старому (DESC). При указании параметра from – по 
умолчанию сортировка выполняется от старого к новому (ASC).  
 
Пример ответа при вызове команды /GET/url/ 
{"took":16,"message":[{"ID":"A6","VALUE":"11","TYPE":11,"EVENT":"2022-06-17 
09:09:12.926"}],"key":"05728174559717465817","status":"success"} 
 
Пример ответа при вызове команды /GET/url/array/ 
{"took":9,"ARRAY":[[{"ID":"A6","VALUE":"11","TYPE":11,"EVENT":"2022-06-17 
09:09:12.926"},{"ID":"A6","VALUE":"2","TYPE":11,"EVENT":"2022-06-17 
09:07:38.009"}]],"message":"success","key":"05728174559717465817","status":"success"}

Работа с хешированными данными 
Для хранения данных высокой дискретности используются хешированные сигналы. Данные сигналы 
хранят и в дальнейшем быстро преобразовывают наборы значений.   
 
Получение исторических данных выполняется путем публикации данных в уникальный вновь 
создаваемый Kafka Topic , который имеет лимитированное время хранения данных , по умолчанию 
72 часа. 
 
 
 
Процесс получения исторических данных состоит из 3 шагов: запрос на формирование исторических 
данных, публикация исторических данных и использование этих данных. Данны й процесс 
схематично представлен на рисунке ниже: 
 
 
 
Пример запроса на получение исторических данных: 
Запрос > 
/publish/url/55-66-77?id=A44|A43&from=2021-02-14 15:00:00&till=2021-02-14 
19:00:00&timebase=1

Введение 
Для целей администрирования хранилища, проверки его состояния, зарегистрированных устройств, 
а также чтения сохраненных сигналов может использоваться WINNUM Cloud Administrator, работа с 
которым доступна через Веб браузер. Для доступа к WINNUM Cloud Administrator необходима 
авторизация. 
 
При подключении к WINNUM Cloud Administrator работы осуществляется со всеми кластерами и дата 
центрами, которые обслуживает данная инсталляция системы. Пример с одним кластером 
представлен на рисунке ниже. 
 
После авторизации в WINNUM Cloud Administrator, в зависимости от прав, пользователю будут 
доступны различные функции и действия. Как видно из примера выше, пользователю доступны 
функции проверки регистрации устройств, а также функционал по работе с сохраненными сигналами 
(перейдем к нему).

указать идентификатор устройства(-изделия) и идентификатор сигнала.
