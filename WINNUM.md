# Работа производственного аналитика через Winnum API

Источник по умолчанию — `winnum`. Сервер запускается без Excel и без подключения к Winnum.
После вопроса AI извлекает намерение, период, станки и операторов. Python проверяет план,
выбирает разрешённые методы, получает только необходимые данные и рассчитывает результат.
AI формулирует ответ по результату расчёта. Он не задаёт адреса, методы API или формулы.

## Настройка на рабочем компьютере

В существующий `.env` добавлены адрес и приложение из проекта. Заполните
`WINNUM_USER` и `WINNUM_PASSWORD` действующими учётными данными с правом чтения.
Все переменные перечислены в `winnum.env.example`. Не заменяйте настройки AI-провайдера.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe winnum_check.py
.\.venv\Scripts\python.exe winnum_check.py --probe
.\.venv\Scripts\python.exe server.py
```

Откройте http://localhost:8000. `--probe` нужен только в сети предприятия: он читает
справочник оборудования. Проверка конкретного станка за завершённую дату:

```powershell
.\.venv\Scripts\python.exe winnum_check.py --probe --machine "3.4" --date 2026-10-01
```

Этот вариант проверяет сводки операторов, состояния за обе смены и комментарии к
интервалам простоев. Он не отправляет производственные данные в AI и не меняет Winnum.
После первого подключения сравните сведения с интерфейсом Winnum: длительности,
границы смен и ФИО. Успех HTTP-запроса сам по себе не подтверждает правильность методики расчёта.

Запуск отдельного вопроса из консоли:

```powershell
.\.venv\Scripts\python.exe main.py --query "На каких станках работал Иванов с 1 по 7 октября 2026?"
```

Excel оставлен как явный совместимый режим: `DATA_SOURCE=excel` для сервера либо
`main.py --source excel путь.xlsx --query "..."`. В режиме Winnum Excel не читается,
резервного переключения на него при ошибке API нет.

## Какие запросы выполняются

| Вопрос | Методы Winnum | Что не загружается |
|---|---|---|
| На каких станках работал оператор за период | `WNApplicationHelper.getProduct`, `WNCNCApplicationOperatorHelper.getOperatorsLoading` по выбранным станкам | Состояния, комментарии и история сигналов |
| В какие дни работал оператор | `getOperatorsLoading` отдельно по календарным дням и станкам | Состояния и комментарии |
| КИМ / загрузка за смену | `WNApplicationTagHelper.getPriorityTagDuration` | ФИО и комментарии |
| Сравнение дня и ночи | `getPriorityTagDuration`, группировка по станку и типу смены | ФИО и комментарии |
| Причины и длительность простоев | `getPriorityTagDuration`, `WNConnectorHelper.getSignal` для A215 только в сменах с простоями | Регистрации операторов и данные заказов |
| Почасовая загрузка | `getPriorityTagDuration`, разбиение интервалов по часам | ФИО и комментарии |

Используется Platform API `/Winnum/views/pages/app/agw.jsp`. Cloud API не требуется.
Методы подтверждены руководством Platform 5.5.3, страницы 15, 24–25, 32–33, 40–41.
Справочник содержит `id`, `name`, `ProductUUID`, кэшируется на 5 минут.
Производственная история не кэшируется и не копируется целиком в базу или Excel.
`POST /api/reload` в режиме Winnum сбрасывает только справочник.

Для операторов API не документирует фильтр по ФИО: сводки получаются по станкам,
затем нужное ФИО выбирает Python. Фамилия допустима, если она однозначна в ответах.
Станок можно указать полным названием или номером перед подчёркиванием/пробелом;
неоднозначное имя требует уточнения. При отсутствии станка рассматриваются доступные
станки приложения в пределах лимита вызовов.

## Периоды и расчёты

- Без дат система уточняет период. Даты могут быть восстановлены из истории `/api/chat`.
  Простая страница сайта отправляет независимые вопросы: период нужно писать в самом вопросе.
- По умолчанию максимум 31 календарный день и 200 вызовов истории на вопрос.
  Настройки: `WINNUM_MAX_DAYS` (1–366), `WINNUM_MAX_REQUESTS` (1–1000).
  Между вызовами проверяется общий бюджет 120 секунд; текущий HTTP-вызов ограничен
  `WINNUM_TIMEOUT` (по умолчанию 30 секунд). Повторные попытки автоматически не выполняются.
- День: 07:00–19:00; ночь: 19:00–07:00 следующего дня. Дата ночи — дата начала.
  `WINNUM_TIMEZONE` задаёт местное время предприятия (по умолчанию Europe/Moscow).
  Времена, полученные от Winnum, трактуются как местные времена предприятия.
- `getPriorityTagDuration` принимает календарные даты. Загружаются только необходимые
  дни, затем интервалы обрезаются по выбранным сменам. Для ночи включается следующий день.
- КИМ = продуктивные минуты / фонд выбранных 12-часовых смен × 100.
  Продуктивные состояния: «Станок под нагрузкой», «Программа выполняется».
  Они соответствуют текущему `ml_core.py`, а не автоматически выбранным тегам.
- Полностью подтверждённый простой даёт КИМ 0. Пропуски и незавершённая смена дают
  `null` и предупреждение, а не выдуманное выключение или окончательный КИМ.
  Продуктивные минуты, фактически полученные за неполный период, показываются отдельно.
- Пересечения разных приоритетных интервалов останавливают расчёт; точные дубликаты удаляются.
  Пропуски покрытия не заполняются состоянием «Станок выключен».
- Сравнение дня и ночи выполняется отдельно для каждого станка. Разница — процентные пункты.
  При неполноте любой группы её итоговый КИМ и соответствующая разница не рассчитываются.
- Сводки операторов относятся к календарным датам. Длительность `value` переводится
  из миллисекунд в минуты. Учитываются любые положительные регистрации (без старого
  порога 30 минут). Это не доказательство присутствия на рабочем месте или продуктивной работы.
- Комментарии A215 сопоставляются с простоем по моменту записи. Это зарегистрированный
  комментарий, а не доказанная причина. Записи вне интервала не приписываются ему.

## Границы первого варианта

Поддержаны шесть согласованных сценариев и почасовая загрузка. Производительность
оператора, его работа по производственным сменам и произвольные границы до часов/минут
пока вызывают уточнение. Для них нужно отдельно проверить получение значения A212
на начало интервала, а затем соединять регистрации с состояниями. Вся история для этого
автоматически не загружается. 1С, ОГМ и кросс-анализ не добавлялись.

Результат `/api/analyze2` включает `answer` и полный структурированный `data` с периодом,
строками, покрытием и предупреждениями. Для текстового ответа в AI передаётся не более
100 элементов каждого раздела; ограничение явно отмечается. В `/api/chat` сохраняется
прежний формат ответа. Учётные данные Winnum не передаются в AI и не выводятся в ошибки.
Комментарии и названия из Winnum считаются недоверенными данными.

Проверка конфигурации не доказывает доступность сервера. Живое подключение в этой
сессии не выполнялось: компьютер находится вне локальной сети предприятия.
Особенно нужно проверить полноту приоритетных интервалов, формат времени, соответствие
A215 комментариям и семантику границ дат в установленной версии Winnum.

## Проверка разработчиком

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m unittest discover -p "test_*.py"
```

Тесты используют ответы XML и заглушки Winnum; сеть и реальные учётные данные не нужны.
