# Журналы приложения и сайта

После перезапуска сервера в каталоге `logs` относительно рабочей папки процесса появляются:

- `access.log`: все HTTP-запросы, дошедшие до приложения, включая сайт, статические файлы, Swagger, API, перенаправления и ошибки. Каждая строка является JSON-объектом.
- `analyst.log`: загрузка данных, этапы аналитики, ошибки AI и сообщения приложения.

HTTP-запись содержит время UTC, метод, путь без query string, код ответа, расшифровку, длительность в миллисекундах, request_id и признак завершённого ответа. Тип исключения добавляется при сбое. Если приложение не начало ответ, status=null: журнал не выдаёт выдуманный код за отправленный клиенту.

Пример полей: `"status": 429, "status_description": "Превышен лимит запросов"`. Частые коды имеют русское пояснение, остальные стандартные коды получают английское название из HTTPStatus. Для нестандартных кодов есть отдельная отметка. Общее описание кода не устанавливает конкретную причину сбоя.

Сервер генерирует новый request_id и возвращает его в заголовке X-Request-ID. По этому значению можно сопоставить HTTP-запись с этапами обработки, в том числе выполняемыми в asyncio.to_thread. Тела запросов, заголовки авторизации и query string HTTP-журнал не сохраняет. Не передавайте секреты в самом пути URL: путь журналируется.

По умолчанию каждый файл ограничен 10 MiB и имеет до пяти архивов (`access.log.1` и т. д.). Настройки до запуска:

```powershell
$env:LOG_DIR = 'C:\ProductAnalyst\logs\A'
$env:LOG_MAX_BYTES = '10485760'
$env:LOG_BACKUP_COUNT = '5'
$env:LOG_LEVEL = 'INFO'
```

Для службы задайте те же переменные в её XML. У службы должны быть права записи. Для A и B используйте разные каталоги. Эта ротация рассчитана на один процесс-писатель, поэтому используйте один worker на экземпляр. HTTP-журнал продолжает записывать все запросы независимо от LOG_LEVEL приложения.

Чтение свежих записей в PowerShell:

```powershell
Get-Content .\logs\access.log -Tail 20 -Wait
Get-Content .\logs\analyst.log -Tail 20 -Wait
```

Старый analyst.log в корне автоматически не переносится. Существующие инструкции, указывающие этот файл, относятся к прежнему варианту журналирования.

Ответы, которые сформировал прокси до обращения к Python, нужно искать в журнале самого прокси. Ошибки JavaScript в браузере этот журнал не собирает. Ошибки AI-провайдера записываются в analyst.log с его HTTP-кодом и пояснением. Код ответа нашего API может отличаться: например, отказ провайдера 429 сейчас преобразуется API чата в 502. Их связывает request_id.
